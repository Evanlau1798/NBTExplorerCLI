# Artifact storage and DAT preparation

`IArtifactStorage` is the Application port for bounded physical artifacts. Infrastructure provides the Windows NTFS implementation; `DatPreparation` uses the port, the existing SourceAddress/TypedEdit/LiteralTranslation contracts, and CompressedNbt. These are service primitives, not an additional public writer command or a substitute for G05's complete plan, backup, journal and recovery engine.

## Explicit lifecycle

Stage checks the exact expected raw preimage and writes a distinct, unpredictable same-directory `.nbtcli-*.candidate` with CreateNew. Artifact input/output stays within 64 MiB. Flush opens the persisted candidate and calls Flush(true). Verify checks its complete staged hash and runs the caller's format/authorization verifier over read-only bytes. Every failed flush clears its previous success; every verification attempt clears the previous verified state. Commit requires successful flush/verify and rechecks candidate/source hashes. No-op retains source bytes and timestamp. Dispose only releases resources and deletes an uncommitted candidate; it never submits data.

Commit uses File.Replace for an existing target, or no-overwrite File.Move for expected-absent creation, then reopens the target and checks the exact postimage. A read handle excludes direct content writes to the source between the final hash check and replace. It permits delete sharing because the OS replacement requires it. Missing/changed sources are conflicts. A replace attempt or readback failure is a distinct ArtifactCommitException: the result may already be the postimage and must be inspected by recovery, not blindly retried. Remaining candidate evidence survives disposal after a replace attempt; a successful replace may have consumed it. The primitive does not provide verified historical backups or a crash journal.

The writer lock is an exclusive handle on the exact root `.nbtcli-writer.lock`. Candidates from one storage instance share its lease, allowing all outputs to be staged before the first commit; another store/process cannot become a concurrent tool writer. All candidates must be disposed to release the lease. The empty lock file remains reusable. This lock does not control Minecraft or other software. The caller must obtain the world's offline/exclusive-writing condition for the whole operation; this primitive does not claim atomic compare-and-swap against an external actor that renames/replaces files between path-based OS calls. Candidate names are internal to the cooperating writer.

## Windows path boundary

Only local fixed/removable drive roots with NTFS are currently validated. DriveType is checked before querying the filesystem or acquiring a writer lease, so mapped network drives and unknown types reject even if their remote filesystem is NTFS. UNC/network, other platforms and other filesystems explicitly reject. Paths are bound to one world ID and an existing parent. Relative paths use the existing Domain grammar; Windows device names and the tool's internal `.nbtcli-` namespace reject. Outer ZIP artifacts and entry names remain separate; this port accepts only physical outer artifacts.

Infrastructure opens every ancestor directory from the volume root with FILE_FLAG_OPEN_REPARSE_POINT and FILE_FLAG_BACKUP_SEMANTICS, checks attributes on the returned handles, and holds them without delete/write sharing for the operation. Artifacts also open with OPEN_REPARSE_POINT and reject reparse/directory handles. A real junction fixture proves that an internal lexical path cannot redirect the operation outside the root; a junction used as the root also rejects. There is no implicit directory creation, extraction or target guessing.

## ZIP verification boundary

ZipArchiveValidation validates an actual archive, not a proposed host-path prefix. It checks a bounded central directory before BCL allocates its entry list, strict UTF-8/CP437 names, exact local/central name and flag agreement, traversal/absolute/device-style entry paths, duplicate names and symlinks. It uses a resettable SharpZipLib inflater to check each Deflate payload's complete end, exact compressed boundary, length and CRC, alongside BCL entry streams for Deflate content validation. Both passes enforce the declared length and cumulative decoded budget. BCL ZIP alone accepts some truncated streams even when decoded length and CRC match. Names are ZIP identities with ordinal case semantics; they are never extracted as host paths. The current profile supports ordinary stored/Deflate single-volume ZIP; ZIP64 EOCD indicators and local/central size sentinels or 0x0001 extras, split/encrypted and other methods explicitly return UnsupportedProfile. Later scanner/pack services must select a supported profile and use this verification on their candidates. This is not a ZIP rewrite or metadata-preservation implementation.

## DAT slice

DatPreparation accepts an exact standalone document binding, explicit compression and preimage, and bounded unique TypedPatch/LiteralPatch operations. It reads a complete typed document, validates operation ownership and original values, applies the existing immutable edits, stages the result, flushes it, and reparses persisted bytes to check the entire authorized result. It returns a verified candidate and never commits. Both a literal translation and an explicit non-text type change are compared against fixed Python struct/gzip postimage bytes. UUID, nonselected values and raw negative-zero bits remain unchanged. Failed preconditions, invalid scope, corrupt input or decode limits do not stage or change the source.

## Evidence and limits

Tests cover real NTFS replace/locked/read-only files and junctions, expected-absent creation, stale/deleted sources, candidate corruption, no-op timestamps, multiple staged outputs per writer and fresh-process readback. Short writes, disk-full after a written prefix, flush failures and errors before/after actual replace are deterministic injected I/O failures against real scratch files. They do not claim physical disk exhaustion or power-loss validation. Fixed binary tree/mutation seeds run under the verification worker's deadline. An isolated copy of current assemblies/fixtures is used for the G02 integration gate without a neighboring legacy checkout.

File.Replace maps to Windows ReplaceFileW. Its WRITE_THROUGH flag is unsupported and some OS error cases have partial outcomes. Flush(true) requests flushing intermediate file buffers; neither establishes hardware power-loss durability, directory-entry durability, multi-artifact atomicity or journal recovery. Those remain separate G05/G08 obligations.
