**NBTExplorerCLI** 的核心設計原則是「絕不盲目覆寫 Minecraft 存檔」。每一筆修改都必須經過 **預覽（Preview）-> 產出計畫（Plan）-> 離線套用（Offline Apply）-> 讀回驗證（Verify）** 的完整流程，並在世界資料夾外自動保存寫前備份與中斷復原日誌。

<WorkflowPipeline kind="edit" lang="zh-tw" />

## 1. 修改存檔前的三大鐵則

1. **永遠先在世界副本（`D:\WorldCopy`）上測試**，確認結果無誤後再對正式存檔操作。
2. **執行任何帶有 `--apply` 或 `apply` 的命令前，請務必關閉 Minecraft 與其他編輯工具**（如地圖編輯器或伺服器程序）。
3. **請勿將 `--state-root` 或 `--output` 檔案放在世界資料夾內部。** 請將計畫檔、收據與狀態目錄存放在世界外的獨立路徑（例如 `D:\Plans` 或 `D:\NbtState`）。

---

## 2. 選取目標節點與使用明確型別（`typed-nbt`）

為了避免將 `Byte` 或 `Short` 誤轉為 `Int` 或 `String` 而導致存檔損壞，`set` 不會從純文字猜測 NBT 型別，而是要求從 `get --types` 回傳的 `data.value` 取出帶有版本標記的 `nbtcli.typed-nbt` 文件，再透過 `--value` 或 `--value-file` 傳入：

```powershell title="PowerShell"
.\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/LevelName --types
```

```json title="由 data.value 取出的範本 (D:\Plans\new-level-name.json)"
{
  "schemaFamily": "nbtcli.typed-nbt",
  "schemaVersion": 1,
  "data": {
    "name": "",
    "root": {
      "tag": "string",
      "value": "Updated Map Name"
    }
  }
}
```

### 選擇節點定址方式

指定 NBT 或 JSON 內部節點時，請從以下兩種定址格式中**擇一使用**：

<Tabs syncKey="selector-kind">
  <TabItem label="JSON Pointer (--pointer)">

標準 RFC 6901 JSON Pointer 語法（以 `/` 分隔層級；若鍵名含 `~` 請轉義為 `~0`，含 `/` 請轉義為 `~1`）：

```powershell title="PowerShell"
.\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/Player/Inventory/0/id --types
```

  </TabItem>
  <TabItem label="結構化區段陣列 (--segments)">

最多可包含 256 個鍵名或陣列索引物件的 JSON 陣列，特別適合包含斜線、句點或特殊字元的標籤名稱：

```powershell title="PowerShell"
.\nbtcli.exe get 'D:\WorldCopy' `
  --path level.dat `
  --segments '[{"kind":"key","key":"Data"},{"kind":"key","key":"Custom.Key"}]' `
  --types
```

  </TabItem>
</Tabs>

若目標為 `.mca` 區塊檔，請同時加上 `--chunk <x,z>`（全域區塊座標）；若直接針對獨立區塊檔查詢，請再加上 `--dimension <namespace:id>`。

## 3. 預覽修改計畫（不改動任何世界檔案）

<SafetyBanner tier="preview" lang="zh-tw" />

<Tabs syncKey="plan-mode">
  <TabItem label="單一節點修改 (set)">

先從 `get --types` 的輸出取出完整的 `data.value`，只修改 `data.root.value` 後存至世界資料夾外的既有目錄（例如 `D:\Plans\new-level-name.json`），接著執行**不加 `--apply`** 的 `set` 命令以產出預覽計畫：

```powershell title="PowerShell"
New-Item -ItemType Directory -Path 'D:\Plans' -Force | Out-Null
$read = .\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/LevelName --types | ConvertFrom-Json
if (-not $read.success) { throw $read.error.message }
$replacement = $read.data.value
$replacement.data.root.value = 'Updated Map Name'
$replacement | ConvertTo-Json -Depth 50 | Set-Content -Encoding utf8 'D:\Plans\new-level-name.json'

.\nbtcli.exe set 'D:\WorldCopy' `
  --path level.dat `
  --pointer /Data/LevelName `
  --value-file 'D:\Plans\new-level-name.json' `
  --output 'D:\Plans\level-name-plan.json'
```

由於未加上 `--apply`，您的世界資料夾完全不會被改動。CLI 會回傳預覽結果（`"preview": true`），並將不可變的修改計畫（`nbtcli.patch-plan`）寫入 `D:\Plans\level-name-plan.json`。

  </TabItem>
  <TabItem label="多節點批次計畫 (plan / batch)">

若需一次修改多個節點，請建立一份包含 1 至 100,000 筆獨立操作（每筆具唯一 `id`）的 `nbtcli.operations` JSON 檔案，並交由 `plan` 或 `batch` 產出批次預覽計畫：

請依[操作集範例](../command-reference/)，用前面的單一節點預覽產生 `D:\Plans\ops.json`。

```powershell title="PowerShell"
New-Item -ItemType Directory -Path 'D:\Plans' -Force | Out-Null
.\nbtcli.exe plan 'D:\WorldCopy' `
  --request 'D:\Plans\ops.json' `
  --output 'D:\Plans\batch-plan.json'
```

  </TabItem>
</Tabs>

## 4. 在離線狀態下套用計畫（`apply`）

檢視完修改計畫並確認 Minecraft 已關閉後，請執行 `apply` 並加上 `--world-offline` 正式寫入：

```powershell title="PowerShell"
.\nbtcli.exe apply 'D:\WorldCopy' `
  --plan 'D:\Plans\level-name-plan.json' `
  --world-offline `
  --output 'D:\Plans\level-name-receipt.json'
```

在執行 `apply` 的過程中，寫入引擎會依序完成四道安全防護：

<Steps>

1. **前置條件與雜湊檢查**

   確認 `D:\WorldCopy` 內的目標檔案 SHA-256 雜湊值與建立計畫時完全一致。若期間檔案曾被外部修改，`apply` 會在寫入任何位元組前立即中止並回傳結束代碼 `3`（`Conflict`）。

2. **寫前備份與暫存候選檔**

   將原始檔案位元組完整存入世界外的 `objects/` 儲存庫，並將更新後的資料寫入暫存候選檔。

3. **寫入復原日誌與原子替換**

   於外部 `journals/` 目錄記錄日誌，接著替換目標世界檔案。

4. **讀回雜湊驗證**

   重新讀取寫入後的檔案，確認雜湊值與計畫預期的結果完全吻合，最後將收據標記為已完成（`"receiptIsTerminal": true`）。

</Steps>

### 認識收據中的九種操作結果計數

每份套用收據都會透過九個互斥的計數欄位，清楚交代所有請求操作的最終狀態：

| 結果欄位 | 白話說明 |
| --- | --- |
| `applied` | 修改已成功寫入磁碟並通過讀回雜湊驗證。 |
| `unchanged` | 目標節點原本就已經是指定的值，經確認無須重複寫入。 |
| `skipped` | 寫前檢查未通過，在動到任何世界檔案前即已略過。 |
| `failed` | 操作於準備或執行階段失敗。 |
| `conflict` | 目標檔案或節點在建立計畫後曾被改動，或發生衝突操作。 |
| `unsupported` | 目標格式或結構不在支援寫入的範圍內。 |
| `cancelled` | 操作被使用者或系統訊號中止（結束代碼 `130`）。 |
| `recoveryRequired` | 寫入途中發生中斷，請執行 `status` 與 `recover`（結束代碼 `7`）。 |
| `rolledBack` | 已透過復原程序將世界完整還原至修改前的狀態（結束代碼 `8`）。 |

## 5. 寫入中斷時的判斷與復原步驟

若 CLI 回傳結束代碼 **`7`（`RECOVERY_REQUIRED`）**，請保持遊戲關閉，並在重試前先檢查復原日誌。若程序被強制終止，可能不會輸出任何回應；無論哪種情況，請使用保存下來的 `--plan-hash` 與相同的 `--state-root`。此復原機制已在 Windows NTFS 檔案系統上通過程序終止測試；斷電（Power Loss）情境則不在已驗證保證範圍內。

若回應包含 `data.pendingPlanHash`，同一世界有另一筆寫入仍待復原。請使用該雜湊與中斷命令原本的狀態目錄執行 `recover`。復原期間世界內可能會有 `.nbtcli-pending-write` 標記，請保留此標記與外部狀態，直到復原完成。

出現 `Conflict` 時，工具會保留外部變更，並繼續阻擋新寫入。如果你已在離線狀態下將整份計畫的檔案還原為經驗證的修改前版本，請再執行 `recover --rollback`。工具確認所有修改前檔案均相符後才解除阻擋，並保留原本的 `Conflict` 回執。

```json title="stdout (RecoveryRequired)"
{
  "schemaFamily": "nbtcli.cli",
  "schemaVersion": 1,
  "success": false,
  "command": "apply",
  "outcome": "RecoveryRequired",
  "data": {
    "planHash": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "recovery": {
      "world": "D:\\WorldCopy",
      "stateRoot": "C:\\Users\\Player\\AppData\\Local\\nbtcli\\worlds\\4a8b9c..."
    }
  },
  "error": {
    "code": "RECOVERY_REQUIRED",
    "message": "World write requires recovery before further use."
  }
}
```

<Steps>

1. **切勿在 Minecraft 中開啟該世界**

   在 Minecraft 中開啟尚未完成寫入的世界會覆寫區塊時間戳記，導致無法乾淨復原。請保持遊戲關閉。

2. **使用 `status` 檢查日誌狀態**

   帶入完全相同的世界路徑、`--plan-hash` 與 `--state-root`（若有自訂狀態目錄）執行 `status`：

   ```powershell title="PowerShell"
   .\nbtcli.exe status 'D:\WorldCopy' `
     --plan-hash 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
   ```

   請一併核對結束代碼、日誌階段（`phase`）、回執與 `repair` 指引，**切勿將未能確認日誌誤判為未曾寫入**：
   - **`journalMayBeAbsent: true`**：表示 CLI 尚未取得回執且無法確認日誌（例如發生日誌讀取或解析錯誤時，即使原日誌已發布且部分檔案已被替換，仍可能出現此值）。
   - **`receiptIsTerminal: false`**：同樣可能出現在找不到日誌或日誌無法讀取的情況，代表最終結果仍未確認。
   - 請保持遊戲關閉，完整保留原本的計畫檔、備份與 `--state-root`。若日誌遺失或無法讀取，請先查明原因；確認原日誌與計畫身分後，再決定執行 `recover` 續寫或 `--rollback` 回滾。

3. **執行 `recover`（選擇繼續完成或完整回滾）**

   <Tabs syncKey="recover-mode">
     <TabItem label="繼續完成寫入 (預設)">

   使用日誌中已暫存的目標內容繼續將修改推進完成：

   ```powershell title="PowerShell"
   .\nbtcli.exe recover 'D:\WorldCopy' `
     --plan-hash 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08 `
     --world-offline
   ```

     </TabItem>
     <TabItem label="完整回滾至修改前狀態 (--rollback)">

   使用寫入開始前保存的原始檔案備份（Preimages）將世界逐位元組完整還原：

   ```powershell title="PowerShell"
   .\nbtcli.exe recover 'D:\WorldCopy' `
     --plan-hash 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08 `
     --rollback `
     --world-offline
   ```

   成功回滾時會回傳**結束代碼 `8`（`RolledBack`）**，讓自動化腳本能明確區分「回滾成功」與「正向套用成功」。

     </TabItem>
   </Tabs>

</Steps>
