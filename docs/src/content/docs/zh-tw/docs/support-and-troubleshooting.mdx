本頁整理了 **NBTExplorerCLI** 支援的 **Minecraft Java Edition** 版本範圍、CLI 剖析驗證與遊戲內實測的責任邊界、所有結束代碼（Exit Codes），以及常見錯誤的排解步驟。

## 1. 支援的 Minecraft Java Edition 版本組合（Profiles）

您可以隨時執行 `nbtcli capabilities`，查詢目前版本註冊的所有命令以及各個 Minecraft `DataVersion` 版本組合（Profile）的宣告支援矩陣：

```powershell title="PowerShell"
.\nbtcli.exe capabilities
```

<ProfileTable lang="zh-tw" />

`capabilities.storageProfiles` 的 `java-classic-anvil` 支援唯讀查閱，適用於儲存格式為 `19133` 且沒有 `DataVersion` 的舊 Anvil 存檔。這些欄位無法判定確切的遊戲版本或指令語法。

已知 Anvil 世界使用 **Java 1.2.5**、**Java 1.5.2**、**Java 1.6.4** 或 **Java 1.8.1** 時，可在 `scan`、`extract` 或 `translate start` 以 `--minecraft-version` 指定確切版本。工作階段及直接翻譯計畫會保留選定版本，供後續開啟與套用。如果舊式內附資源包不在翻譯範圍內，可用 `--types` 選擇世界文字角色。Java 1.2.5 可直接修改原版告示牌，其餘列出的版本也支援書本、顯示欄位和可辨識的指令文字參數。

Java 1.2.5、1.5.2 和 1.6.4 的告示牌使用純文字。譯文每行最多 15 個 UTF-16 碼元，且不得換行。Java 1.5.2 和 1.6.4 的純文字書名及每頁分別最多 16 和 256 個碼元。計分板顯示名稱最多 32 個碼元，隊伍前綴及後綴各最多 16 個碼元。若實體名稱是選擇器的識別值，請保留原名。套用後請用對應版本的原版遊戲驗證指令能否執行。

對於有序及無序工作台配方，`scan` 和 `validate` 會依資料包已登錄的格式檢查產物物品欄位。若該欄位缺漏、格式無效或指定為空氣，會回報 `InvalidRecipeResult`。物品是否存在、材料與堆疊數量是否合法，以及資料包間的交互作用，仍由對應版本的 Minecraft 伺服器驗證。

### 如何解讀 `capabilities` 的支援宣告

針對每一個版本組合，`capabilities` 會分別回報五種操作階段（`read`、`extract`、`plan`、`write`、`recover`）與六種資料面向（`layout`、`itemSchema`、`textSchema`、`commandGrammar`、`compression`、`packLayout`）：

- **「可讀取」不等於「可寫入」**：請勿因為 `get` 或 `list` 能讀取某個檔案，就假設該格式一定支援修改。規劃器（Planner）與寫入器（Writer）在產生與套用計畫前，皆會嚴格檢查該目標角色、文字結構與版本組合是否具備寫入支援。
- **CLI 剖析器驗證 vs. 遊戲內實機驗證的邊界**：
  - `validate`、`scan`、`plan` 與 `apply` 會在命令列層級驗證二進位 NBT／區塊結構、JSON 語法、SHA-256 寫前與寫後雜湊，以及資料結構規範。
  - 通過 CLI 驗證**並不能取代**實際開啟 Minecraft Java Edition 遊戲客戶端進行測試。凡是尚未在執行中的遊戲內載入測試過的視覺排版、字型寬度與指令觸發行為，皆屬於**尚待實機驗證**狀態——在正式發布地圖前，請務必於 Minecraft 遊戲內實地載入世界副本確認效果。

## 2. 支援的 21 種世界文字角色（Text Roles）

執行 `scan`、`extract`、`validate`、`convert` 或 `translate start` 時，可透過 `--types` 參數指定篩選以下 21 種文字角色中的任意組合：

- **方塊與告示牌**：`Sign`、`HangingSign`、`ContainerName`、`CommandBlock`
- **書本與講台**：`Book`、`LecternBook`、`Title`、`Author`
- **物品與實體**：`ItemName`、`ItemLore`、`ArmorStand`、`EntityName`、`TextDisplay`
- **世界與介面狀態**：`BossBar`、`ScoreboardTeam`、`ScoreboardObjective`
- **資料包與語言資源**：`McFunction`、`Advancement`、`CommandStorage`、`LangKey`、`TranslationKey`

## 3. 結束代碼（Exit Codes）完整對照表

每次執行指令時，除了標準輸出（`stdout`）上的 JSON 回應外，程序也會回傳明確的結束代碼。當結束代碼非 `0`（即 `success: false`）時，請檢查 JSON 內的 `error.code`、`error.message` 與 `error.details` 取得詳細原因。

## 4. 常見錯誤與疑難排解步驟

### 情境 A：世界檔案被鎖定或拒絕存取（結束代碼 `5`）

**常見現象**：執行 `scan`、`backup` 或 `apply` 時失敗，並回傳結束代碼 `5`（`IO_ERROR` 或 `ACCESS_DENIED`）。

<Steps>

1. 完全關閉 Minecraft Java Edition 遊戲視窗、單人整合伺服器或獨立伺服器程序。
2. 關閉其他正在開啟同一個世界資料夾的工具（例如其他 NBT 檢視器、地圖算繪器或壓縮軟體）。
3. 對您的世界副本重新執行該指令。

</Steps>

### 情境 B：寫入途中發生中斷 — `RECOVERY_REQUIRED`（結束代碼 `7`）

**常見現象**：執行 `apply` 或 `recover` 時回傳結束代碼 `7`（`RECOVERY_REQUIRED`）。

<Steps>

1. **請勿在 Minecraft 遊戲中開啟該世界。**
2. 記下 JSON 輸出中的 `planHash` 與 `stateRoot`。
3. 執行 `nbtcli status <world> --plan-hash <hash> --state-root <stateRoot>` 檢查復原日誌狀態。
4. 執行 `nbtcli recover <world> --plan-hash <hash> --state-root <stateRoot> --world-offline` 繼續完成寫入，或加上 `--rollback` 完整退回修改前的原始檔案狀態（成功回滾會回傳結束代碼 `8`）。

</Steps>

### 情境 C：產生計畫或建立工作階段後，世界曾被外部修改（結束代碼 `3`）

**常見現象**：執行 `apply` 或 `translate submit` 時失敗，並回傳結束代碼 `3`（`CONFLICT`）。

**發生原因**：在您建立 `patch-plan` 或開啟翻譯工作階段之後，磁碟上的世界檔案曾被其他程式改動。為了保護存檔，NBTExplorerCLI 絕不會拿過期的計畫去覆寫已變更的檔案。

**排解步驟**：
- 若是一般編輯計畫過期：請對目前的世界檔案重新執行 `get --types` 與 `set` / `plan`，產生新的計畫檔。
- 若是翻譯工作階段快照過期（提示 `repair: "start-new-session"`）：請對更新後的世界副本重新執行 `translate start` 開啟新工作階段；依[地圖翻譯工作流](../translation-workflow/)中的翻譯記憶範例，帶入新工作階段 ID、該工作階段的完整 slot 雜湊、舊工作階段 ID 與術語表版本號。

### 情境 D：區塊或 NBT 檔案損壞，或包含未支援格式（結束代碼 `4` 或 `5`）

**常見現象**：`scan` 或 `validate` 回報 `coverageComplete: false`，並回傳結束代碼 `4`（未支援的版本或特性）或結束代碼 `5`（檔案損壞，例如 0 位元組的 `.mca` 區塊檔或語法錯誤的資料包 JSON）。

<Steps>

1. 執行 `nbtcli validate <world>`，檢視 JSON 輸出中每個來源檔案的診斷結果，找出是哪一個相對路徑發生問題。
2. 若是單一檔案損壞且您先前已建立過備份，可執行 `nbtcli restore <world> --manifest-hash <hash> --path <相對路徑> --apply --world-offline` 單獨修復該檔案。
3. 若您只需要翻譯或修改其他正常的維度或特定檔案，可使用 `--dimension`、`--region`、`--path` 或 `--types` 將操作範圍限定在正常檔案上。

</Steps>

### 情境 E：超過記憶體／輸出上限或正規表示式配對逾時（結束代碼 `6`）

**常見現象**：指令回傳結束代碼 `6`（`RESOURCE_LIMIT` 或 `PATTERN_TIMEOUT`）。

**發生原因**：為防止記憶體耗盡或複雜正規表示式造成卡死，NBTExplorerCLI 設有 64 MiB 單檔／輸出上限、100,000 個翻譯槽位上限、256 層節點深度上限，以及 100 毫秒正規表示式配對逾時保護。

**排解步驟**：
- 透過 `--dimension`、`--region`、`--path` 或 `--types` 縮小單次處理的目標範圍。
- 建立或匯出翻譯工作階段時，調降 `--page-size` 或 `--page-bytes`。
- 簡化 `--match-pattern` 中的正規表示式寫法。
