Adventure maps often contain hundreds or thousands of lines spread across signs, books, named items, NPCs, scoreboards, bossbars, command blocks, and datapacks. **NBTExplorerCLI** collects all of that text into a **Translation Project (Session)** saved safely outside your world folder, splits it into small pages, and protects all colors, click events, and command syntax automatically.

Your Minecraft save is **not modified at all** until the final step when you explicitly apply your finished translation plan.

## Step 1: Start a Translation Project (`translate start`)

Run `translate start` on your copied world folder (`D:\WorldCopy`). You can omit `--source-language` and `--target-language`: the CLI automatically detects the source language from recognizable content (or uses `und` if undetermined), picks your current Windows account display language as the target, and binds both languages to the session. Pass explicit language flags only when you want to override them:

```powershell title="PowerShell"
# Automatic source detection + Windows account display language
.\nbtcli.exe translate start 'D:\WorldCopy' --page-size 30

# Explicit override for the Japanese-to-English example below
.\nbtcli.exe translate start 'D:\WorldCopy' `
  --source-language ja `
  --target-language en-US `
  --page-size 30
```

You will get back a JSON response like this (showing an example targeting `en_us`):

```json title="Output"
{
  "schemaFamily": "nbtcli.cli",
  "schemaVersion": 1,
  "success": true,
  "command": "translate",
  "outcome": "Success",
  "data": {
    "status": {
      "sessionId": "6f9619ff-8b86-d011-b42d-00cf4fc964ff",
      "revision": 0,
      "total": 60,
      "pending": 60
    },
    "sourceLocale": "ja",
    "targetLocale": "en_us"
  },
  "error": null
}
```

Write down your **`sessionId`** — you will pass it to the next commands.
- `sourceLocale` / `targetLocale`: The resolved language pair bound when the session is created. Resuming the same session later keeps these bound languages even if your system display language changes. If Windows does not provide a usable display language, the CLI prompts in English to pass `--target-language <language>`.
- `und` source: When the source language cannot be proven (for example, short labels or mixed text), `sourceLocale` is set to `und`. You can still translate by reading the original text, or start a new session with an explicit `--source-language`.
- `total`: Total number of text items found across the map.
- `pending`: How many items are still waiting to be translated.
- `revision`: Progress counter that goes up by `1` each time you submit a page.

:::note[Why Your Formatting and Commands Stay Safe]
Every individual sign line, book page, or item name gets its own `slotId`, so even two identical source lines can be translated differently depending on context. You only edit the plain text — underlying Minecraft colors, hover/click events, scores, and selectors are kept safely hidden inside the tool so a typo cannot break map mechanics.
:::

## Step 2: Export a Page and Fill In Translations

<Steps>

1. **Export Page 0 (`translate export`)**

   First create an external folder (`D:\Translate`) to hold your working files, then export page `0` and save its ready-to-fill reply file (`reply-0.json`):

   ```powershell title="PowerShell"
   # Create a working folder outside your world
   New-Item -ItemType Directory -Path 'D:\Translate' -Force | Out-Null

   # Export page 0 (replace the session ID with yours)
   $export = .\nbtcli.exe translate export 'D:\WorldCopy' `
     --session-id '6f9619ff-8b86-d011-b42d-00cf4fc964ff' `
     --page 0 `
     --output 'D:\Translate\page-0-prompt.txt' | ConvertFrom-Json

   if (-not $export.success) { throw $export.error.message }

   # Save the ready-to-fill reply template
   $export.data.replyTemplate | ConvertTo-Json -Depth 50 |
     Set-Content -Encoding utf8 'D:\Translate\reply-0.json'
   ```

   - `page-0-prompt.txt` shows each line's original text, context, and English translation instructions (CLI guidance is fixed in English regardless of map languages).
   - `reply-0.json` is the template you edit and send back, retaining the session's bound `targetLocale` and IDs.

2. **Fill In `reply-0.json`**

   Open `D:\Translate\reply-0.json` in Notepad or VS Code. Keep all ID fields (`operationId`, `sessionId`, `slotId`, `sourceTextHash`, etc.) unchanged, and keep every item in the `slots` list:
   - **If you translated an item**: set `"state": "translated"` and put your translation in `"text"`.
   - **If you want to keep the original text as-is** (such as a proper name or symbol): set `"state": "unchanged"` and `"text": null`.

3. **Submit the Completed Page (`submit` or `advance`)**

   <Tabs syncKey="submit-mode">
     <TabItem label="Submit This Page (submit)">

   ```powershell title="PowerShell"
   .\nbtcli.exe translate submit 'D:\WorldCopy' `
     --session-id '6f9619ff-8b86-d011-b42d-00cf4fc964ff' `
     --reply 'D:\Translate\reply-0.json'
   ```

     </TabItem>
     <TabItem label="Submit & Get Next Page Together (advance)">

   `translate advance` submits your finished reply and immediately returns the next unfinished page in one command (or call it without `--reply` anytime to see the next unfinished page):

   ```powershell title="PowerShell"
   .\nbtcli.exe translate advance 'D:\WorldCopy' `
     --session-id '6f9619ff-8b86-d011-b42d-00cf4fc964ff' `
     --reply 'D:\Translate\reply-0.json'
   ```

     </TabItem>
   </Tabs>

   Repeat Step 2 for each page until `pending` drops to **`0`**. You can stop anytime and continue another day — all progress is saved automatically outside your world.

</Steps>

:::caution[Do Not Edit the World While Translating]
Each time you submit a page, `nbtcli` checks that the world files have not changed since you started. If you edit the world externally mid-translation, `submit` stops safely with exit code `3` (`Conflict`) while keeping all your saved translations so you can start a new session and reuse them with `translate memory`.
:::

## Step 3: Apply Your Finished Translations to the Map

Once `pending` reaches `0`, check your latest `revision` number with `translate status`:

```powershell title="PowerShell"
.\nbtcli.exe translate status 'D:\WorldCopy' --session-id '6f9619ff-8b86-d011-b42d-00cf4fc964ff'
```

Then finish in three clear steps:

<Steps>

1. **Build the Update Plan (`translate plan`)**

   Choose how you want players to see the translation:

   <Tabs syncKey="translate-plan-mode">
     <TabItem label="Replace Text Directly in the Map (--direct)">

   **Easiest for players**: Writes translated text straight into the map so players do not need to install any resource pack:

   ```powershell title="PowerShell"
   $opId = [guid]::NewGuid().ToString()

   .\nbtcli.exe translate plan 'D:\WorldCopy' `
     --session-id '6f9619ff-8b86-d011-b42d-00cf4fc964ff' `
     --revision 2 `
     --direct `
     --operation-id $opId `
     --output 'D:\Translate\world-translate-plan.json'
   ```

     </TabItem>
     <TabItem label="Use Translation Keys + Resource Pack (--keys)">

   Converts map text into translation keys and bundles the matching `.json` language file inside a resource pack. This example uses `en_us.json`. If `translate start` returned a different `targetLocale`, use that value for the filename. See **[Resource Packs & Language Files](../resources-and-packs/)**.

   ```powershell title="PowerShell"
   $opId = [guid]::NewGuid().ToString()

   .\nbtcli.exe translate plan 'D:\WorldCopy' `
     --session-id '6f9619ff-8b86-d011-b42d-00cf4fc964ff' `
     --revision 2 `
     --keys `
     --prefix map. `
     --language-output 'resources.zip#assets/adventure/lang/en_us.json' `
     --operation-id $opId `
     --output 'D:\Translate\world-translate-plan.json'
   ```

     </TabItem>
   </Tabs>

   *(If you only want a standalone `.zip` resource pack or bilingual language files without modifying the map at all, jump to **[Resource Packs & Language Files](../resources-and-packs/)** for `export-lang` and `create-pack`. When a session's `sourceLocale` is `und`, pass `--original-lang <language>` explicitly to those commands.)*

2. **Close Minecraft and Apply the Plan (`apply`)**

   <SafetyBanner tier="write" lang="en" />

   Make sure Minecraft is completely closed, then run:

   ```powershell title="PowerShell"
   .\nbtcli.exe apply 'D:\WorldCopy' `
     --plan 'D:\Translate\world-translate-plan.json' `
     --world-offline `
     --output 'D:\Translate\world-translate-receipt.json'
   ```

   Open your copied world in Minecraft to verify that signs, books, items, and dialogue look great in-game!

3. **Mark the Translation Project as Done (`translate seal`)**

   Once `apply` succeeds (exit code `0`), run `translate seal` with the same `--revision`, `--operation-id`, and the plan's `planHash`:

   ```powershell title="PowerShell"
   $planHash = (Get-Content -Raw 'D:\Translate\world-translate-plan.json' | ConvertFrom-Json).data.planHash

   .\nbtcli.exe translate seal 'D:\WorldCopy' `
     --session-id '6f9619ff-8b86-d011-b42d-00cf4fc964ff' `
     --revision 2 `
     --operation-id $opId `
     --plan-hash $planHash
   ```

   `seal` double-checks that the world update truly completed before closing the project.

</Steps>

## Draft Text From an Unresolved Source (`translate fallback`)

Use `translate fallback` when a scan can read an artifact (or standalone file) but cannot establish how its text is used. The selected tag or line is returned as context (`data.context`), along with editable candidate paths (`data.candidates`), any unverified branches (`data.unverified`), and a versioned reply template (`data.replyTemplate`, `nbtcli.translation-draft-reply` v2). It supports NBT, JSON, SNBT, and UTF-8 text.

Just like `translate start`, you can omit `--source-language` and `--target-language` to resolve languages automatically and bind them into `draftId`, `sourceLocale`, and `targetLocale`, or pass explicit override flags:

```powershell title="Standalone NBT file: export draft, designate a confirmed custom field, and validate a reply"
# 1. Export context and recognized translatable text leaves under /dialogue
.\nbtcli.exe translate fallback 'D:\dialogue.nbt' --pointer /dialogue

# 2. If a custom field under the selection is confirmed as display text, specify its relative path with --text-pointer
.\nbtcli.exe translate fallback 'D:\dialogue.nbt' --pointer /dialogue --text-pointer /caption

# 3. Validate a completed reply (reuses the bound languages and requires the same selection and --text-pointer)
.\nbtcli.exe translate fallback 'D:\dialogue.nbt' --pointer /dialogue --text-pointer /caption --reply 'D:\reply.json'
```

You can also target a specific line inside a world's datapack function (or a ZIP member via `--entry`, a region chunk via `--chunk x,z`, or a zero-based UTF-8 `--byte-range start,length`):

```powershell title="World datapack function line"
New-Item -ItemType Directory -Path 'D:\Drafts' -Force | Out-Null

.\nbtcli.exe translate fallback 'D:\WorldCopy' `
  --path 'datapacks/story/data/story/functions/dialogue.mcfunction' --line 12 `
  --output 'D:\Drafts\dialogue-context.json'

.\nbtcli.exe translate fallback 'D:\WorldCopy' `
  --path 'datapacks/story/data/story/functions/dialogue.mcfunction' --line 12 `
  --reply 'D:\Drafts\dialogue-reply.json' --output 'D:\Drafts\dialogue-validated.json'
```

Key validation and safety rules:
- **Selection and `--text-pointer`**: For an NBT or JSON file, use `--pointer` (or omit it to inspect the root). The selection provides full context, while replies may only edit recognized translatable text leaves unless you explicitly designate a confirmed custom display field with a relative `--text-pointer` (such as `/caption`). Repeat the exact same selection and `--text-pointer` when submitting `--reply`.
- **Language binding**: Copy `data.replyTemplate` to a separate JSON file, fill in `text` for slots you translate (leaving unchanged slots as `null`), and preserve `draftId`, `sourceLocale`, `targetLocale`, `slotId`, and `sourceTextHash`. Submitting `--reply` without language flags reuses the draft's bound languages even if your system display language changes; explicit language flags must match.
- **Layered protection**: Formatting codes, placeholders, numbers, private-use glyphs, Roman level suffixes, and unproven custom fonts are protected. Unknown-purpose fields or malformed/ambiguous inner branches are preserved untouched and listed in `data.unverified` (setting `structureVerified: false`), while valid sibling leaves remain translatable. Explicit `--format text` drafts also report `structureVerified: false`.
- **Line, byte-range, and SNBT options**: Line numbers start at `1` and select a trailing structured command operand by default (keeping one physical line on output). Use `--format snbt` (and optional `--snbt-profile`) for standalone SNBT snippets, or `--byte-range start,length` with `--format json|snbt|text`.
- **Formal apply boundary**: Place draft exports outside Minecraft world folders even for individual files. Validated drafts return the rewritten snippet in `data.content` with `gameplayVerified: false`, leave the original artifact and whole-world scan verdict intact, and still require meeting formal apply conditions before editing a save.

For several selections in one world, use `translate fallback <world> --batch draft-batch.json`. The request uses `schemaFamily: "nbtcli.translation-draft-batch"`, `schemaVersion: 1`, and a `selections` array. Each selection contains the whole file's SHA-256 as `sourceHash` and an `options` object, for example `{"path":"datapacks/example/data/demo/functions/read.mcfunction","line":"12"}`. An archive selection also needs its member's `entryHash`. Use the returned `data.drafts` in selection order. To validate translations, copy a draft's `replyTemplate` to the corresponding selection's `reply` field, fill the slot texts, and run the same command again. Batch requests accept up to 1,024 selections and use the same read-only draft validation as a single selection.

Add `--session-id <id>` and the session's `--state-root` if you used a custom location. The batch inherits the session languages and returns `data.sessionReplySlots` for each translated leaf that matches an exact slot in the current world snapshot. Merge those rows by `slotId` into the corresponding reply templates from `translate export`, then submit each complete page with `translate submit`. Stale sources, ambiguous matches, and leaves without a verified slot fail validation. The session plan and apply steps check the sources again before writing.

## Helpful Extras (Optional)

You do not need any of these to finish a map translation, but they are handy on large projects:

- **Translate only part of a map**: Add `--dimension`, `--region`, `--types`, `--path`, or `--match-pattern` to `translate start` (for example, `--types Sign,Book` to translate only signs and books).
- **Classic Minecraft maps**. Pass the game's release to `translate start`, for example `--minecraft-version 1.8.9`. See [Supported Versions](../support-and-troubleshooting/) for accepted releases and plain-text character limits.
- **Check progress or view related lines**:
  - Progress: `.\nbtcli.exe translate status 'D:\WorldCopy' --session-id <id>`
  - One specific slot: `.\nbtcli.exe translate get 'D:\WorldCopy' --session-id <id> --slot-id <slot-id>`
  - Grouped context (same book/sign): `.\nbtcli.exe translate groups 'D:\WorldCopy' --session-id <id> --limit 50`

### Reading or Updating Glossary and Notes

```powershell title="PowerShell"
# Read saved glossary terms or translator notes
.\nbtcli.exe translate glossary 'D:\WorldCopy' --session-id '<session-id>'
.\nbtcli.exe translate note 'D:\WorldCopy' --session-id '<session-id>'
```

To add glossary terms, add notes, jump to a page, or reset selected slots back to unfinished, pass a `nbtcli.session-command` JSON file via `--request` to `translate glossary`, `translate note`, `translate jump`, or `translate reset` (add `--confirm` to execute a reset). See the template in **[Command Reference](../command-reference/)**.

### Reusing Translations From an Earlier Session (`translate memory`)

If the map was updated and you started a new translation session, look up matching translations from an earlier session:

```powershell title="PowerShell"
.\nbtcli.exe translate memory 'D:\WorldCopy' `
  --session-id '<current-session-id>' `
  --slot-id '<full-slot-id>' `
  --source-sessions '<previous-session-id>' `
  --glossary-version '<glossary-version>'
```

### Saving Client Preferences for External Tools (`agent`)

If you use scripts or AI assistants on a world, you can optionally store local client preferences (such as `preferredItemsPerPage` and suggested language metadata) with `agent`:

```powershell title="PowerShell"
New-Item -ItemType Directory -Path 'D:\Translate' -Force | Out-Null

# 1. Export the preference questionnaire (defaults sourceLanguage to "auto" and targetLanguage to your Windows display language; optionally add --source-language / --target-language)
.\nbtcli.exe agent setup 'D:\WorldCopy' `
  --output 'D:\Translate\agent-questionnaire.json'

# 2. Fill in configuration.agentName inside the file, then save it
.\nbtcli.exe agent submit 'D:\WorldCopy' --request 'D:\Translate\agent-questionnaire.json'

# 3. Check saved preferences anytime
.\nbtcli.exe agent status 'D:\WorldCopy'
```

`agent` commands only save settings locally inside your state folder — they never connect to the internet or modify your world. Note that omitting language flags on `translate start` still uses automatic source detection and your Windows display language; pass explicit language options when overriding for a session.
