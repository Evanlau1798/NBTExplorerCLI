<SafetyBanner tier="write" lang="en" />

**NBTExplorerCLI** never blindly overwrites your Minecraft world. Every edit follows a simple **Preview first, Apply second** workflow — think of it like reviewing your shopping cart before clicking Pay. Before anything is written to disk, the tool automatically backs up the original files outside your world folder so you can recover or undo cleanly if anything interrupts the write.

<WorkflowPipeline kind="edit" lang="en" />

## 1. Three Simple Safety Rules

1. **Always test on a copy** (like `D:\WorldCopy`) before editing your real save.
2. **Close Minecraft completely** (and any other map editors) before running `apply` or `--apply`.
3. **Keep plan and output files outside your world folder** (for example, in `D:\Plans`), never inside `D:\WorldCopy`.

---

## 2. Why Editing Uses `get --types` First

Minecraft save files are picky about data types — for example, a number might specifically need to be a `Byte` (`0`/`1`), `Short`, `Int`, or `String`. Guessing the wrong type can corrupt a save.

Instead of making you guess, `nbtcli` lets you read the existing value with `--types`, change just the value inside it, and pass it straight back to `set`. That way the exact Minecraft tag type is preserved automatically!

### Picking What to Edit (`--pointer`)

Point to a field inside an NBT or JSON file just like a folder path using `--pointer` (separate each level with `/`):

<Tabs syncKey="selector-kind">
  <TabItem label="Normal Path (--pointer)">

```powershell title="PowerShell"
# Example: read the first item ID in the player's inventory inside level.dat
.\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/Player/Inventory/0/id --types
```

*(If a field name contains `~`, write `~0`; if it contains `/`, write `~1`.)*

  </TabItem>
  <TabItem label="Special Key Names (--segments)">

If a tag name contains dots, slashes, or unusual punctuation, pass an explicit JSON array of key/index steps with `--segments`:

```powershell title="PowerShell"
.\nbtcli.exe get 'D:\WorldCopy' `
  --path level.dat `
  --segments '[{"kind":"key","key":"Data"},{"kind":"key","key":"Custom.Key"}]' `
  --types
```

  </TabItem>
</Tabs>

*(When editing a region chunk `.mca`, also add `--chunk x,z` and `--dimension minecraft:overworld` if targeting a standalone `.mca` file.)*

## 3. Step-by-Step: Preview and Apply an Edit

<SafetyBanner tier="preview" lang="en" />

Let's walk through changing a world's display name (`LevelName`) inside `level.dat`. Notice how every line is clearly labeled:

<Tabs syncKey="plan-mode">
  <TabItem label="Single Value Edit (set)">

```powershell title="Step 1: Preview the change (world stays untouched)"
# 1. Make an external folder for our plan files
New-Item -ItemType Directory -Path 'D:\Plans' -Force | Out-Null

# 2. Read the current LevelName along with its exact NBT type
$read = .\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/LevelName --types | ConvertFrom-Json
if (-not $read.success) { throw $read.error.message }

# 3. Put your new title into the value field and save it to a file
$replacement = $read.data.value
$replacement.data.root.value = 'Updated Map Name'
$replacement | ConvertTo-Json -Depth 50 | Set-Content -Encoding utf8 'D:\Plans\new-level-name.json'

# 4. Build the preview plan (no --apply means your world is NOT touched!)
.\nbtcli.exe set 'D:\WorldCopy' `
  --path level.dat `
  --pointer /Data/LevelName `
  --value-file 'D:\Plans\new-level-name.json' `
  --output 'D:\Plans\level-name-plan.json'
```

  </TabItem>
  <TabItem label="Multiple Edits at Once (plan / batch)">

To bundle multiple edits (up to 100,000) into one atomic plan, create an `nbtcli.operations` file (see the copy-paste helper in **[Command Reference](../command-reference/)**) and preview it with `plan`:

```powershell title="PowerShell"
New-Item -ItemType Directory -Path 'D:\Plans' -Force | Out-Null

.\nbtcli.exe plan 'D:\WorldCopy' `
  --request 'D:\Plans\ops.json' `
  --output 'D:\Plans\batch-plan.json'
```

  </TabItem>
</Tabs>

Now that the plan is ready, **make sure Minecraft is closed**, then apply it:

```powershell title="Step 2: Apply the reviewed plan offline"
.\nbtcli.exe apply 'D:\WorldCopy' `
  --plan 'D:\Plans\level-name-plan.json' `
  --world-offline `
  --output 'D:\Plans\level-name-receipt.json'
```

What happens automatically behind the scenes during `apply`:
1. **Checks nothing changed** since you created the plan (if Minecraft or another tool edited the world meanwhile, `apply` stops safely before writing anything).
2. **Saves an automatic backup** of the original files outside your world folder.
3. **Writes the updated files and verifies** every written byte matches the plan.

## 4. What If a Write Stops Halfway? (Crash Recovery)

If your terminal closes unexpectedly during `apply`, or you ever see **exit code `7` (`RECOVERY_REQUIRED`)**, do not panic! Your original files were backed up automatically before writing began.

Follow these three calm steps:

<Steps>

1. **Keep Minecraft Closed!**

   Do **not** launch the world in Minecraft while recovery is pending — opening the world could change chunk files and make automatic recovery harder.

2. **Check the Status (`status`)**

   Grab the `planHash` (or `data.pendingPlanHash` if shown) from the output — or from your saved `plan.json` — and check what happened:

   ```powershell title="PowerShell"
   .\nbtcli.exe status 'D:\WorldCopy' `
     --plan-hash '<YOUR-PLAN-HASH>'
   ```

   *(If you passed a custom `--state-root` earlier, pass that exact same `--state-root` here too.)*

3. **Choose: Finish the Edit OR Undo Everything (`recover`)**

   <Tabs syncKey="recover-mode">
     <TabItem label="Finish Applying the Edit (Default)">

   Completes the planned changes cleanly:

   ```powershell title="PowerShell"
   .\nbtcli.exe recover 'D:\WorldCopy' `
     --plan-hash '<YOUR-PLAN-HASH>' `
     --world-offline
   ```

   Returns exit code **`0`** when finished.

     </TabItem>
     <TabItem label="Undo & Restore Original World (--rollback)">

   Restores your world byte-for-byte back to how it was before `apply` started:

   ```powershell title="PowerShell"
   .\nbtcli.exe recover 'D:\WorldCopy' `
     --plan-hash '<YOUR-PLAN-HASH>' `
     --rollback `
     --world-offline
   ```

   Returns exit code **`8` (`RolledBack`)** so you (and any scripts) can clearly tell it was rolled back rather than applied forward.

     </TabItem>
   </Tabs>

</Steps>

<details>
<summary>Advanced Technical Details: Commit Phases, 9 Receipt Counters, and Edge-Case Recovery</summary>

### Internal Four-Stage Commit Pipeline

1. **Precondition & Hash Verification**: Confirms target files still match the SHA-256 hashes recorded in `plan.json` (fails with exit code `3` / `Conflict` if altered).
2. **Preimage Backup & Staging**: Copies original bytes into `<stateRoot>\objects\` and writes staged candidate files.
3. **Journal Publication & Atomic Replace**: Writes the recovery journal in `<stateRoot>\journals\` and replaces target files.
4. **Readback Verification**: Re-reads every target file to prove hashes match planned postimages, then marks `"receiptIsTerminal": true`.

### Nine Receipt Outcome Counters

| Field | Meaning |
| --- | --- |
| `applied` | Written and verified on disk. |
| `unchanged` | Target already matched the requested value; no write needed. |
| `skipped` | Pre-commit validation rejected the plan before any world file was touched. |
| `failed` | Operation failed during preparation or execution. |
| `conflict` | Target file or node changed since preview, or had a competing edit. |
| `unsupported` | Target format/structure is not supported for writing. |
| `cancelled` | Recorded as cancelled (exit code `130`). |
| `recoveryRequired` | Interrupted mid-commit; run `status` and `recover` (exit code `7`). |
| `rolledBack` | `recover --rollback` restored the verified pre-edit bytes (exit code `8`). |

### Edge-Case Recovery Notes

- **Scope of testing**: Recovery is verified after process termination on Windows NTFS; sudden hardware power loss has not been verified.
- **`.nbtcli-pending-write` marker**: While a write is pending recovery, the world folder may contain a `.nbtcli-pending-write` marker and block new writes (`data.pendingPlanHash`). Keep that marker and your external state directory together until `recover` finishes.
- **Unconfirmed journals (`journalMayBeAbsent: true` or `receiptIsTerminal: false`)**: Do **not** assume nothing was written if `status` cannot confirm the journal (for example, due to a read/parse error). Keep Minecraft closed, preserve your plan, backup, and state root, and confirm the original journal identity before running `recover`.
- **Clearing a `Conflict` block**: A `Conflict` preserves external changes and keeps new writes blocked. If you manually restore the plan's verified preimages offline, re-run `recover --rollback` to verify them and release the write block (preserving the original `Conflict` receipt).

</details>
