**NBTExplorerCLI** is designed so that you never overwrite a Minecraft world blindly. Every modification follows a strict **Preview -> Plan -> Offline Apply -> Verify** workflow, backed by automatic pre-write backups and a crash recovery journal stored outside your world folder.

<WorkflowPipeline kind="edit" lang="en" />

## 1. Golden Rules Before Editing

1. **Always test on a world copy** (`D:\WorldCopy`) before modifying an important save.
2. **Close Minecraft and any other external tools** (such as map editors or server processes) before running any command with `--apply` or `apply`.
3. **Never place `--state-root` or `--output` files inside the world folder.** Keep plans, receipts, and state folders in a separate directory such as `D:\Plans` or `D:\NbtState`.

---

## 2. Selecting Nodes and Using Explicit Typed NBT

To prevent accidental data corruption (such as turning a `Byte` or `Short` tag into an `Int` or `String`), `set` does not guess NBT types from plain strings. Instead, extract the exact `nbtcli.typed-nbt` document from `data.value` returned by `get --types` and pass it via `--value` or `--value-file`:

```powershell title="PowerShell"
.\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/LevelName --types
```

```json title="Extracted data.value (D:\Plans\new-level-name.json)"
{
  "schemaFamily": "nbtcli.typed-nbt",
  "schemaVersion": 1,
  "data": {
    "name": "",
    "root": {
      "tag": "string",
      "value": "Updated Map Name"
    }
  }
}
```

### Choosing a Node Selector

When targeting a node inside an NBT or JSON file, provide **one** selector format:

<Tabs syncKey="selector-kind">
  <TabItem label="JSON Pointer (--pointer)">

Standard RFC 6901 JSON Pointer syntax (`/` separates keys; escape `~` as `~0` and `/` as `~1`):

```powershell title="PowerShell"
.\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/Player/Inventory/0/id --types
```

  </TabItem>
  <TabItem label="Explicit Segments (--segments)">

Structured JSON array of up to 256 key/index objects for tag names containing slashes, dots, or special characters:

```powershell title="PowerShell"
.\nbtcli.exe get 'D:\WorldCopy' `
  --path level.dat `
  --segments '[{"kind":"key","key":"Data"},{"kind":"key","key":"Custom.Key"}]' `
  --types
```

  </TabItem>
</Tabs>

For region files (`.mca`), also specify `--chunk <x,z>` (global chunk coordinates) and, when querying standalone region files, `--dimension <namespace:id>`.

## 3. Previewing an Edit (No World Files Modified)

<SafetyBanner tier="preview" lang="en" />

<Tabs syncKey="plan-mode">
  <TabItem label="Single Node Edit (set)">

Save the `data.value` returned by `get --types`, modify only `data.root.value`, write it to an existing directory outside the world (`D:\Plans\new-level-name.json`), and then run `set` **without** `--apply` to generate a preview plan:

```powershell title="PowerShell"
New-Item -ItemType Directory -Path 'D:\Plans' -Force | Out-Null
$read = .\nbtcli.exe get 'D:\WorldCopy' --path level.dat --pointer /Data/LevelName --types | ConvertFrom-Json
if (-not $read.success) { throw $read.error.message }
$replacement = $read.data.value
$replacement.data.root.value = 'Updated Map Name'
$replacement | ConvertTo-Json -Depth 50 | Set-Content -Encoding utf8 'D:\Plans\new-level-name.json'

.\nbtcli.exe set 'D:\WorldCopy' `
  --path level.dat `
  --pointer /Data/LevelName `
  --value-file 'D:\Plans\new-level-name.json' `
  --output 'D:\Plans\level-name-plan.json'
```

Because `--apply` was omitted, your world folder is completely untouched. The CLI outputs a preview envelope (`"preview": true`) and writes the immutable `nbtcli.patch-plan` file to `D:\Plans\level-name-plan.json`.

  </TabItem>
  <TabItem label="Multi-Node Batch Plan (plan / batch)">

For multi-node edits, create a `nbtcli.operations` JSON file (containing 1 to 100,000 operations with distinct `id` values) and pass it to `plan` or `batch`:

Use the [operation-set example](../command-reference/) to generate `D:\Plans\ops.json` from the single-node preview shown above.

```powershell title="PowerShell"
New-Item -ItemType Directory -Path 'D:\Plans' -Force | Out-Null
.\nbtcli.exe plan 'D:\WorldCopy' `
  --request 'D:\Plans\ops.json' `
  --output 'D:\Plans\batch-plan.json'
```

  </TabItem>
</Tabs>

## 4. Applying the Plan Offline

Once you have reviewed the plan and confirmed that Minecraft is closed, commit the plan with `apply` and `--world-offline`:

```powershell title="PowerShell"
.\nbtcli.exe apply 'D:\WorldCopy' `
  --plan 'D:\Plans\level-name-plan.json' `
  --world-offline `
  --output 'D:\Plans\level-name-receipt.json'
```

During `apply`, the engine performs four safety steps in order:

<Steps>

1. **Precondition & Hash Verification**

   Confirms that the target files in `D:\WorldCopy` still match the exact SHA-256 hashes recorded when the plan was created. If a file was modified externally, `apply` stops with exit code `3` (`Conflict`) before writing anything.

2. **Preimage Backup & Candidate Staging**

   Stores the original file bytes in the external `objects/` repository and writes the updated data to temporary staged candidate files.

3. **Journal Publication & Atomic Replace**

   Records the transaction in the external `journals/` directory and replaces the target world files.

4. **Readback Verification**

   Re-reads the written files to prove their hashes match the planned postimages, then marks the receipt terminal (`"receiptIsTerminal": true`).

</Steps>

### Understanding the Nine Operation Outcomes

Every apply receipt accounts for all requested operations across nine mutually exclusive outcome counters:

| Outcome Field | Plain-Language Meaning |
| --- | --- |
| `applied` | The change was written and verified on disk. |
| `unchanged` | The target already had the requested value; verified with no physical write needed. |
| `skipped` | Pre-commit validation rejected the plan before any world file was touched. |
| `failed` | An operation failed during preparation or execution. |
| `conflict` | The target file or node changed since the plan was created, or had a competing edit. |
| `unsupported` | The operation targets a format or structure that is not supported for writing. |
| `cancelled` | The operation was recorded as cancelled (exit code `130`). |
| `recoveryRequired` | The write was interrupted mid-commit; run `status` and `recover` (exit code `7`). |
| `rolledBack` | Recovery restored the world to its verified pre-edit state (exit code `8`). |

## 5. How to Judge and Recover After an Interrupted Write

If the CLI returns exit code **`7` (`RECOVERY_REQUIRED`)**, keep the game closed and inspect the journal before retrying. A process that is terminated may produce no response. Use the saved plan hash and the same state root in either case. Recovery has been tested after process termination on Windows NTFS. Recovery after power loss has not been verified.

```json title="stdout (RecoveryRequired)"
{
  "schemaFamily": "nbtcli.cli",
  "schemaVersion": 1,
  "success": false,
  "command": "apply",
  "outcome": "RecoveryRequired",
  "data": {
    "planHash": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "recovery": {
      "world": "D:\\WorldCopy",
      "stateRoot": "C:\\Users\\Player\\AppData\\Local\\nbtcli\\worlds\\4a8b9c..."
    }
  },
  "error": {
    "code": "RECOVERY_REQUIRED",
    "message": "World write requires recovery before further use."
  }
}
```

<Steps>

1. **Keep the World Closed in Minecraft**

   Opening a partially updated world in Minecraft can overwrite chunk timestamps and prevent clean recovery. Keep the game closed.

2. **Inspect the Journal State with `status`**

   Run `status` with the exact same world path, `--plan-hash`, and `--state-root` (if you used a custom state root):

   ```powershell title="PowerShell"
   .\nbtcli.exe status 'D:\WorldCopy' `
     --plan-hash 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
   ```

   Inspect the exit code, journal `phase`, `receipt`, and `repair` guidance together—do **not** assume an unconfirmed journal means nothing was written:
   - **`journalMayBeAbsent: true`** means the CLI did not receive a receipt and could not confirm the journal (for example, due to a journal read or parse error even when the original journal was already published and some files were replaced).
   - **`receiptIsTerminal: false`** can likewise appear when a journal is missing or unreadable, leaving the outcome unresolved.
   - Keep Minecraft closed and preserve your original plan, backup, and state root. If a journal is missing or unreadable, investigate before proceeding, and run `recover` (forward complete or `--rollback`) only after confirming the original journal and plan identity.

3. **Run `recover` (Forward Complete or Roll Back)**

   <Tabs syncKey="recover-mode">
     <TabItem label="Complete Forward (Default)">

   Finish applying the staged postimages recorded in the journal:

   ```powershell title="PowerShell"
   .\nbtcli.exe recover 'D:\WorldCopy' `
     --plan-hash 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08 `
     --world-offline
   ```

     </TabItem>
     <TabItem label="Roll Back to Pre-Edit State (--rollback)">

   Restore the exact original world files byte-for-byte from the verified preimage backups stored before the write began:

   ```powershell title="PowerShell"
   .\nbtcli.exe recover 'D:\WorldCopy' `
     --plan-hash 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08 `
     --rollback `
     --world-offline
   ```

   A successful rollback returns **exit code `8` (`RolledBack`)** so automated scripts never mistake a rollback for a forward edit.

     </TabItem>
   </Tabs>

</Steps>
